# Migrating JiraFlow v0.5 to v1

JiraFlow v1 migrates only signatures proven from tag `v0.5.0`. Preview first:

```bash
jira-flow migrate
jira-flow migrate --json
```

Confirm interactively or use the explicit headless form:

```bash
jira-flow migrate --yes
```

The setup TUI performs the same inspection and presents the planned changes.

## Recognized legacy artifacts

- the exact POSIX `commit-msg` wrapper invoking the `commitmsg` helper;
- a `commit-msg` symlink whose target basename is exactly `commitmsg`;
- the exact POSIX `post-checkout` wrapper invoking `postco`;
- a `post-checkout` symlink whose target basename is exactly `postco`.

The wrappers must contain the exact historical shebang/invocation and no extra
lines, operators, or trailing content. See the frozen
[signature catalog](v0.5-signatures.md).

## Result

An eligible migration revalidates the snapshot immediately before mutation,
removes only recognized legacy artifacts, installs the v1 owned `commit-msg`,
and initializes `enabled=true`, `mode=hybrid`. A recognized legacy
`post-checkout` is removed; v1 never replaces it.

v0.5 did not durably store Manual issue/mode state, so migration never invents
it. Link the current worktree explicitly after migration if needed.

If v1 initialization fails, JiraFlow restores the exact wrapper bytes,
executable mode, and symlink targets it removed. If the hooks change between
preview and mutation, migration refuses.

## Ambiguous or foreign hooks

Any added shell content, different helper, unsupported file type, mixed legacy
and foreign logic, or ordinary user hook blocks all migration changes. JiraFlow
does not guess ownership or partially remove a legacy-looking setup. Preserve
the hook, migrate its user logic manually if desired, then run normal
`jira-flow init` with the explicit composition flags.

After migration:

```bash
jira-flow status
jira-flow doctor
git commit --allow-empty -m "chore: verify JiraFlow v1"
```
