### Review Scope

The review covers the current public main branch, including the Go CLI, Git-hook binaries, repository configuration model, status/toggle behavior, tests, npm wrapper and installers, GoReleaser, GitHub Actions release/publish workflows, Homebrew formula, Dockerfile, and release history.

The goal is not to nitpick formatting. The focus is on behavior a user could reasonably depend on: whether configuration survives, whether commits are modified correctly, whether hooks coexist safely, whether documented commands work, whether installation paths are valid, and whether releases can be trusted.

## 1. Executive Summary

JiraFlow has a strong and useful product idea: automatically connect Git commits to Jira issue keys with minimal developer friction. However, the current v0.5.0 implementation should be treated as a prototype rather than a stable foundation. The biggest problems are not cosmetic. Several user-facing features are only partially wired, configuration is not persistent, hook ownership is unsafe, documented commands are broken, and the distribution/release paths disagree with one another.

The central architectural mistake is that JiraFlow currently conflates four separate concerns: installation state, repository configuration, current branch state, and ownership of Git hooks. Those concerns need independent models. Once separated, the package can become dramatically smaller, safer, and easier to test.

A patch-by-patch repair is possible, but it would preserve unnecessary complexity. The recommended path is a v1 refactor/rewrite that keeps the product idea and useful issue-key extraction behavior while replacing the three-binary architecture, ephemeral configuration model, current hook-management logic, and release pipeline.

## 3. Detailed Findings 1-24

The following findings are ordered roughly from core product correctness through Git integration, distribution, and release tooling. They intentionally include both observed defects and design flaws that make defects likely.

### 1. Automatic configuration wrongly depends on the current branch

**P1 - High  The branch/configuration problem you remembered is real.**

ConfigureAutomatic() sets AutoLink and then immediately reads the current branch as a configuration-time test.

Only main and master are explicitly allowed without a Jira issue key. Any other branch must already contain a matching key or configuration returns an error.

That means perfectly legitimate branches such as develop, trunk, release/1.2, feature/login, or chore/update-deps can prevent JiraFlow from being enabled.

This is the wrong lifecycle. Enabling automatic linking should configure future commit behavior; it should not require the branch used during setup to already satisfy the runtime matching rule.

```text
Current conceptual flow:

jira-flow init
  -> ConfigureAutomatic()
  -> read current branch
  -> require Jira key unless branch is exactly main/master
```

**Why this matters.** A user can be unable to enable JiraFlow merely because they ran init while standing on a non-ticket branch.

**Recommended direction.** Installation should be branch-agnostic. Branch inspection belongs in commit-time behavior, not setup validation.

**Source references:** *internal/jira.go*; *internal/cli.go*

### 2. Manual mode is not actually wired into commit behavior

**P0 - Critical  The UI accepts a manual issue key, but the installed commit behavior does not use it.**

Manual configuration sets jiraManager.Config.JiraKey and AutoLink=false only in the process running the interactive CLI.

No repository file, Git config entry, or other persistent state records those values.

Later, the commit-msg hook runs as a separate process. It does not load the manual key. Instead, it always obtains the current branch and extracts a Jira key from that branch using its own hard-coded regex.

The result is a feature that can report success in the interactive setup while behaving as automatic branch mode at commit time.

```text
Current behavior:

init -> manual -> Config.JiraKey = "ABC-123" -> process exits
commit-msg -> ignore prior Config -> inspect branch -> prepend branch-derived key
```

**Why this matters.** A user who selected manual mode cannot rely on the entered ticket association being applied to commits.

**Recommended direction.** Persist repository mode and the linked issue key. A dedicated `jira-flow link ABC-123` command is cleaner than treating a manual key as one-time init input.

**Source references:** *internal/cli.go*; *hooks/commitmsg/main.go*; *internal/config.go*

### 3. Config is an in-memory defaults object, not persistent repository configuration

**P0 - Critical  The Config type suggests a durable configuration model, but no durable state exists.**

Config contains AutoLink, JiraKey, BranchPattern, and HookPath, but NewConfig() simply returns defaults.

The post-checkout hook creates a fresh default Config every time it runs.

The commit-msg hook bypasses JiraManager configuration and compiles a hard-coded Jira regex independently.

This creates multiple definitions of JiraFlow behavior that can disagree and makes user choices disappear when the CLI exits.

**Why this matters.** The product cannot reliably support repository-specific mode, patterns, issue associations, or future options.

**Recommended direction.** Define a single persistent repo config/state source and make every runtime path load it. Git-local config or private state under .git are good fits.

**Source references:** *internal/config.go*; *hooks/post_checkout/main.go*; *hooks/commitmsg/main.go*

### 4. Setup and removal can destroy other tools' Git hooks

**P0 - Critical  JiraFlow writes directly to hook paths without establishing ownership or preserving existing hooks.**

SetCommitMsgHook and SetPostCheckoutHook ultimately call os.WriteFile on .git/hooks/commit-msg and .git/hooks/post-checkout.

There is no check for an existing Husky, lefthook, pre-commit, commitlint, company, or custom hook; no backup; no chaining; and no warning.

Removal later deletes the same paths without proving they belong to JiraFlow.

The tool can therefore replace an existing hook during init and delete the replacement path during remove, permanently losing the user's prior hook.

**Why this matters.** This is destructive repository behavior and is serious enough to block recommending the current package for public use.

**Recommended direction.** Adopt an explicit hook-coexistence strategy. At minimum detect ownership and refuse destructive writes; ideally compose with existing hooks or use a managed hook directory.

**Source references:** *internal/git.go*; *internal/utils.go*

### 5. Status can report JiraFlow active when the hooks are unrelated

**P1 - High  Presence is treated as ownership.**

IsJiraFlowActive() and CheckStatus() only test whether files named commit-msg and post-checkout exist.

They do not inspect contents, executable targets, metadata, repository configuration, or an ownership marker.

A repository with arbitrary hooks using those names can be reported as JiraFlow active even if JiraFlow has never been initialized.

That false positive combines dangerously with removal logic that can delete those files.

**Why this matters.** Status output is not trustworthy and can mislead later destructive operations.

**Recommended direction.** Determine active state from persisted JiraFlow configuration plus verified managed hook integration, not generic filename existence.

**Source references:** *internal/status.go*

### 6. The documented `jira-flow status --toggle` command is broken

**P1 - High  The implementation checks positional args for `--toggle` but never registers a Cobra flag.**

README.md documents `jira-flow status --toggle`.

The status command's Run function checks whether args[0] equals `--toggle`.

Cobra normally parses tokens beginning with -- as flags and rejects unknown flags before Run is invoked.

Because the command never registers a `toggle` flag, the documented path should not reach the toggle logic.

**Why this matters.** A documented control path is effectively dead.

**Recommended direction.** Prefer explicit `enable` and `disable` commands. If toggle is retained, register it as a real Cobra flag and test it end-to-end.

**Source references:** *README.md*; *cmd/app/main.go*

### 7. JiraFlow has two different hook installation models

**P1 - High  Init/configure and status-toggle do not produce the same repository state.**

SetGitHooks() generates shell scripts that execute helper binaries.

ToggleJiraFlow(enable=true) instead creates symlinks directly to the helper binaries.

The two code paths have different behavior, platform requirements, failure modes, and ownership characteristics.

A user can therefore reach different hook layouts depending on how JiraFlow was enabled.

**Why this matters.** The package has duplicated state transitions that can drift and behave differently across operating systems.

**Recommended direction.** There should be one hook installation abstraction and one repository state model.

**Source references:** *internal/git.go*; *internal/status.go*

### 8. Running init from a repository subdirectory can install hooks in the wrong place

**P1 - High  Repository validation discovers the correct root, but installation still uses relative `.git/hooks`.**

CheckGitAndHooksDir() correctly calls `git rev-parse --show-toplevel` and validates the root repository hook directory.

However, Config.HookPath defaults to `.git/hooks/`, and SetGitHooks() later writes relative to the current working directory.

From `repo/apps/web`, JiraFlow can validate `repo/.git/hooks` but then create `repo/apps/web/.git/hooks` and install scripts there.

Git will not execute those hooks because they are outside the repository's actual Git directory.

**Why this matters.** Initialization can report success while installing inert hooks.

**Recommended direction.** Resolve hook paths through Git, e.g. `git rev-parse --git-path hooks`, and use that resolved absolute path consistently.

**Source references:** *internal/git.go*; *internal/config.go*

### 9. Worktrees and `core.hooksPath` are not handled

**P1 - High  The implementation assumes every repository uses a literal `.git/hooks` directory.**

Git worktrees may use a `.git` file that points elsewhere rather than a local `.git` directory.

Users and hook managers can configure `core.hooksPath` to relocate hooks.

JiraFlow's hard-coded relative path ignores both cases.

Modern Git tooling should ask Git where its hook directory is instead of reconstructing it.

**Why this matters.** JiraFlow can silently fail or interfere with repositories that use valid Git configurations.

**Recommended direction.** Use Git's own path resolution and treat custom hook paths as first-class.

**Source references:** *internal/config.go*; *internal/git.go*; *internal/status.go*

### 10. The post-checkout hook currently provides almost no functional value

**P2 - Medium  Commit-time behavior already reads the current branch, so checkout-time tracking is redundant.**

The commit-msg hook calls GetCurrentBranchName() at the moment a commit is being created.

The post-checkout hook merely inspects the new branch and prints a message about an extracted issue key.

It does not persist branch state that commit-msg later consumes.

Maintaining a second hook therefore doubles integration surface without materially enabling the core feature.

**Why this matters.** JiraFlow occupies an extra hook, increases the chance of conflicts, and complicates distribution for little benefit.

**Recommended direction.** Remove post-checkout unless a future feature has a concrete checkout-time requirement.

**Source references:** *hooks/commitmsg/main.go*; *hooks/post_checkout/main.go*

### 11. The post-checkout hook contains unreachable control flow

**P3 - Low  One branch of the final conditional cannot execute.**

The hook exits immediately when issue-key extraction returns an error.

It then checks `if err == nil { ... } else { ... }`.

The `else` branch is unreachable because every non-nil error already exited.

**Why this matters.** This is minor on its own, but it is a signal that this path has not been exercised carefully.

**Recommended direction.** Delete the redundant branch; preferably remove the entire post-checkout hook as described above.

**Source references:** *hooks/post_checkout/main.go*

### 12. Go hook resolution unnecessarily depends on npm

**P1 - High  The native Go CLI finds helper binaries by querying npm's global installation path.**

GetGlobalBinPath() runs `npm -v`, `npm bin -g`, or `npm config --global get prefix`.

getBinaryPath() then uses that result for commitmsg and postco, even if JiraFlow was installed with Homebrew, a manual release asset, curl, or another non-npm mechanism.

The error from GetGlobalBinPath() is discarded in getBinaryPath().

This means native Git-hook behavior can implicitly depend on npm existing and being configured.

**Why this matters.** Installation methods are not independent and errors can degrade into invalid hook paths.

**Recommended direction.** Use a single executable and resolve it using `os.Executable()` or install a stable shim that invokes `jira-flow hook ...`.

**Source references:** *internal/utils.go*; *internal/git.go*

### 13. Releasing three binaries creates avoidable package complexity

**P2 - Medium  The helper-binary design leaks into every distribution path.**

Current releases build `jiraflow`, `commitmsg`, and `postco` separately.

npm installation, npm uninstall, Homebrew, shell scripts, PowerShell, Docker, GoReleaser, and hook generation all need to know about all three.

Each extra binary multiplies naming, packaging, path-resolution, signing, and compatibility problems.

**Why this matters.** A simple commit transformation tool has a disproportionately large release surface.

**Recommended direction.** Ship one `jira-flow` binary with an internal `hook commit-msg` subcommand.

**Source references:** *.goreleaser.yml*; *scripts/install.js*; *scripts/uninstall.js*; *installScripts/**

### 14. Commit-message mutation is not idempotent

**P2 - Medium  The hook blindly prepends the Jira key every time it processes a message.**

prependIssueKeyToCommitMsg() replaces the first line with `<issueKey> <existing first line>`.

It does not check whether the message already starts with that key or already references the ticket.

Amending or reprocessing an existing message can therefore create repeated prefixes.

**Why this matters.** Commit history can accumulate duplicated Jira keys such as `ABC-123 ABC-123 feat: ...`.

**Recommended direction.** Detect existing references before mutation and make commit processing idempotent.

**Source references:** *hooks/commitmsg/main.go*

### 15. Prepending the Jira key can break Conventional Commits and release tooling

**P2 - Medium  The chosen formatting strategy assumes the Jira reference must appear before the existing subject.**

A valid message such as `feat(auth): add login` becomes `ABC-123 feat(auth): add login`.

Many Conventional Commit parsers expect the type to begin the subject.

This can interfere with commitlint, semantic-release, release-please, changelog tooling, or internal commit-policy automation.

**Why this matters.** JiraFlow can solve Jira linking while breaking another common piece of developer workflow.

**Recommended direction.** Make formatting configurable or use a reference format that preserves established commit syntax.

**Source references:** *hooks/commitmsg/main.go*

### 16. Manual Jira-key validation is not strict whole-input validation

**P2 - Medium  Branch extraction and manual-entry validation incorrectly share a substring-oriented regex.**

ValidateJiraKey() uses the same BranchPattern and regexp.MatchString().

The default pattern is not anchored, so input containing a valid-looking key substring can satisfy the check even if the full input should be considered invalid.

Manual entry and branch scanning are different problems: manual entry should validate the entire token; branch extraction should search within a larger branch name.

**Why this matters.** Invalid manual input can be accepted and future customization becomes harder to reason about.

**Recommended direction.** Separate strict Jira-key validation from branch issue-key extraction.

**Source references:** *internal/jira.go*; *internal/config.go*

### 17. A configurable invalid regex can panic the process

**P2 - Medium  Issue-key extraction uses regexp.MustCompile().**

MustCompile is appropriate only when the pattern is a programmer-controlled constant that is guaranteed valid.

Config already models BranchPattern as configuration and a future v1 would likely expose it.

If a user-supplied or corrupted pattern is invalid, MustCompile will panic instead of returning a recoverable configuration error.

**Why this matters.** A configuration mistake can crash JiraFlow inside a Git hook.

**Recommended direction.** Compile and validate patterns when configuration is set, using regexp.Compile() and explicit errors.

**Source references:** *internal/git.go*

### 18. Commit-message reading can truncate data in edge cases

**P1 - High  The commit hook uses bufio.Scanner, ignores scanner.Err(), then truncates and rewrites the file.**

Scanner has a token-size limit unless its buffer is increased.

The code does not check scanner.Err() after the scan loop.

It then reopens the same file with os.Create(), truncating it before writing the collected lines.

A scan failure or unusually long line can therefore result in only a partial message being written back.

**Why this matters.** An edge-case commit message can be destructively rewritten.

**Recommended direction.** Use os.ReadFile/os.WriteFile for this small file or check every read/write error before truncating.

**Source references:** *hooks/commitmsg/main.go*

### 19. Hook installation is not transactional

**P2 - Medium  A partial installation can be left behind if one hook succeeds and the next fails.**

SetGitHooks() installs commit-msg first and post-checkout second.

There is no rollback if the second operation fails.

The repository can therefore be left in an unreported or half-configured state.

**Why this matters.** Users can end up with partial integration that status and remove logic may interpret incorrectly.

**Recommended direction.** Use a transactional install/rollback strategy, or simplify to one hook so the state transition is atomic.

**Source references:** *internal/git.go*

### 20. The Unix/macOS quick installer requests release assets that do not exist

**P1 - High  The shell installer naming scheme does not match GoReleaser output.**

The installer downloads names such as `jira-flow-$OS-$ARCH`, `commitmsg-$OS-$ARCH`, and `postco-$OS-$ARCH` from the latest release.

GoReleaser publishes versioned `.tar.gz` archives using binary names such as `jiraflow_0.5.0_darwin_arm64.tar.gz`.

The installer also treats the response as a directly executable binary rather than an archive.

**Why this matters.** The documented curl installer is not aligned with the artifacts the release pipeline actually publishes.

**Recommended direction.** Generate installer URLs from the real release manifest or remove the custom installer until it is tested end-to-end.

**Source references:** *installScripts/unix/install.sh*; *.goreleaser.yml*

### 21. The Windows installer has the same release-asset mismatch

**P1 - High  PowerShell expects uncompressed `.exe` files with names GoReleaser does not publish.**

The installer requests `jira-flow-windows-amd64.exe`, `commitmsg-windows-amd64.exe`, and `postco-windows-amd64.exe`.

GoReleaser publishes versioned tar.gz archives under a different binary naming convention.

As with the Unix installer, the release contract and installation contract are disconnected.

**Why this matters.** The advertised Windows quick-install path is unreliable.

**Recommended direction.** Either publish matching platform-native assets or make the installer extract the actual GoReleaser archives.

**Source references:** *installScripts/windows/install.ps1*; *.goreleaser.yml*

### 22. The Homebrew formula is incompatible with current release artifacts

**P1 - High  The formula's URL, archive contents, binary names, and test assumptions disagree with GoReleaser.**

The formula expects files such as `jira-flow-darwin-arm64.tar.gz`, while releases are named like `jiraflow_0.5.0_darwin_arm64.tar.gz`.

It downloads one archive but attempts to install `jira-flow`, `commitmsg`, and `postco`, even though GoReleaser packages those as separate archives.

The main Go binary is built as `jiraflow`, not `jira-flow`.

The formula is therefore not describing the actual artifact layout.

**Why this matters.** The formula in this repository cannot be treated as a reliable representation of the current release.

**Recommended direction.** Generate/tap a formula from the same single-binary GoReleaser release rather than maintaining a parallel hand-authored artifact contract.

**Source references:** *installScripts/homebrew/jira-flow.rb*; *.goreleaser.yml*

### 23. Homebrew tests a nonexistent version path, and the CLI requires a Git repo too early

**P1 - High  Informational CLI commands are coupled to repository state.**

The Homebrew formula tests `jira-flow --version`, but the Cobra root command does not define a version.

Before Cobra processes any arguments, main() checks `git rev-parse --is-inside-work-tree` and exits if the current directory is not a Git repository.

That means help/version-style commands cannot be clean global CLI operations outside a repository.

**Why this matters.** Package managers cannot reliably smoke-test the executable, and basic CLI discovery is unnecessarily constrained.

**Recommended direction.** Move Git-repository validation into only the subcommands that require a repo, and add a real version command/flag populated from build metadata.

**Source references:** *installScripts/homebrew/jira-flow.rb*; *cmd/app/main.go*

### 24. Docker is stale and does not fit the hook lifecycle well

**P1 - High  The Dockerfile builds a Go 1.22.1 module using Go 1.19, and the container model does not naturally solve host Git-hook execution.**

go.mod declares Go 1.22.1.

The Docker builder image is golang:1.19-alpine.

Even after correcting the Go version, running `jira-flow init` in a container would create hooks in a mounted repository that later need a runnable JiraFlow command when host Git invokes them.

That makes Docker a poor distribution mechanism for this particular local Git-hook tool unless additional host integration is designed.

**Why this matters.** The current Docker support is both stale and conceptually awkward for the product.

**Recommended direction.** Remove Docker from supported installation methods unless there is a specific container-native use case worth maintaining.

**Source references:** *go.mod*; *installScripts/docker/Dockerfile*; *README.md*

## 4. Versioning and Releasing Need a Rethink

Versioning is currently spread across several mechanisms that are only loosely connected. The repository simultaneously contains a package.json version, Git tags and GitHub releases, a hard-coded Homebrew version, an npm install-script placeholder, GoReleaser naming, a manual version-bump shell script, and Changesets configuration. This creates multiple opportunities for drift.

### Current competing sources of truth

```text
package.json       -> 0.5.0
Git tag            -> v0.5.0
GitHub Release     -> v0.5.0
Homebrew formula   -> 0.5.0
npm package        -> package.json-driven
install.js         -> %%VERSION%% placeholder replaced during publish
GoReleaser         -> derives artifact version from tag
Changesets         -> separate versioning/changelog mechanism
```

### Specific release-system problems

- The manual prepublish script invokes an interactive version bump, commits package.json, creates a signed Git tag, and pushes it. This makes release correctness depend on local operator state and GPG configuration.
- Changesets exists but is not the authoritative release mechanism. A stale changeset remains in the repository, so there are effectively two release philosophies at once.
- The Changesets config declares `access: restricted` despite jira-flow being a public npm package.
- GitHub's release workflow builds assets from tags, while npm publishing is triggered by release creation and separately patches install.js with the current package.json version.
- The Homebrew formula has its own hard-coded version and artifact naming expectations.
- The Go binary itself does not expose a trustworthy runtime version.

**Source references:** *scripts/prepublish.sh*; *.changeset/config.json*; *.changeset/cool-pumpkins-speak.md*; *.github/workflows/release.yml*; *.github/workflows/publish.yml*; *package.json*

### Recommended release model

For a small Go CLI, the release process should have one canonical version event: a semver Git tag. Everything else should derive from that tag.

```text
release PR / version decision
        |
        v
semver Git tag (vX.Y.Z)
        |
        v
GoReleaser
  -> GitHub release + checksums/signature
  -> single platform binary/archive contract
        |
        +--> npm wrapper/package publish
        +--> Homebrew formula/tap update
        +--> optional install script generated from same artifact names
```

The binary should receive version/commit/date metadata at link time so `jira-flow version` can report exactly what is installed. Changesets is unnecessary unless JiraFlow becomes a multi-package JavaScript workspace; for this repository it adds more state than value.

## 5. Testing Is Not Trustworthy Yet

The repository has tests, but several of them do not protect the user-facing behavior the package depends on. More importantly, there is no ordinary CI workflow that gates commits/releases with build and test results.

### Concrete test-quality problems

The clearest example is TestSetGitHookScript in tests/git_test.go. The table defines a `script` input with both a valid and empty script, but that value is never passed into the code under test. Both cases simply call `internal.SetGitHooks(config)` while expecting different outcomes. The test therefore does not test the condition described by its table.

**Source references:** *tests/git_test.go*

That same test uses NewConfig(), whose HookPath is `.git/hooks/`. Unless the environment happens to prevent it, a test can operate on the actual checkout's hooks rather than a fully isolated temporary repository.

**Source references:** *tests/git_test.go*; *internal/config.go*

TestCLIMenuOutput creates fake stdin and then calls CheckStatus() directly rather than driving CLIMenu or the Cobra command. It therefore does not meaningfully verify the interactive menu path suggested by the test name.

**Source references:** *tests/cli_test.go*

Toggle tests mock InstallHooks by creating dummy files, which verifies the wrapper logic but does not exercise the actual hook-installation implementation, symlink behavior, generated shell scripts, Windows behavior, or ownership semantics.

**Source references:** *tests/cli_test.go*; *tests/jira_flow_test.go*; *internal/status.go*

### Missing tests that matter

- End-to-end init from repository root and nested subdirectories.
- Automatic mode setup while currently on main, develop, trunk, release branches, ticket branches, and detached HEAD.
- Manual link persistence across separate processes.
- Commit-msg behavior after automatic and manual configuration.
- Idempotent commit rewriting and amend flows.
- Conventional Commit preservation/configuration.
- Existing hook coexistence and ownership detection.
- core.hooksPath and Git worktree behavior.
- Repository removal that leaves foreign hooks untouched.
- Cross-platform artifact installation against the exact files produced by GoReleaser.
- npm install/uninstall smoke tests.
- Homebrew formula smoke tests.
- CLI help/version behavior outside Git repositories.

### Missing CI gate

The GitHub workflows visible in the repository are release/publish workflows. There is no normal pull-request/push CI workflow that clearly gates changes with tests and static checks before a tag can be released.

```text
Minimum v1 CI gate:
  go test ./...
  go vet ./...
  staticcheck or golangci-lint
  build supported targets
  integration tests in temporary Git repositories
  GoReleaser check
  installer/release artifact smoke tests where practical
```

**Source references:** *.github/workflows/release.yml*; *.github/workflows/publish.yml*

Note: this review did not claim an observed `go test ./...` result from a local clone. The important point is that the defects above are visible directly in the repository's test source and workflow configuration.

## 6. Smaller Architecture and UX Issues

Beyond the 24 primary findings, the repository contains smaller inconsistencies that are worth cleaning up during the v1 consolidation.

| **Issue** | **Observation** |
| --- | --- |
| Unused parameters | CheckStatus(config) accepts a Config value but does not use it. |
| Duplicated hook-removal concepts | RemoveGitHooks() and RemoveHooks() are separate implementations with different call sites. |
| Duplicated hook-install concepts | SetGitHooks() writes generated scripts while InstallHooks creates symlinks. |
| Ignored errors | Several calls deliberately discard errors with `_`, including global binary path lookup and branch/key extraction in success messaging. |
| Double error reporting | CheckGitAndHooksDir prints an error and returns it, then callers print another higher-level error. |
| Inconsistent naming | The repository alternates among jira-flow, jiraflow, JiraFlow, and JIRA in executable names, UI, archives, and documentation. |
| Stale npm metadata | package.json declares `main: index.js`, but the package is a CLI wrapper and no index.js is part of the reviewed root. |
| Fragile npm uninstall | removeBinary() finds the first filename by prefix and then constructs a path even when no match is found. |
| No checksum verification during npm installation | Checksums/signature are published, but install.js downloads binaries without verifying them. |
| Noisy hook output | Hooks print messages during routine checkout/commit operations where silent success would be friendlier. |
| Over-coupled root command | The top-level executable validates Git-repository state before it knows which command the user asked for. |
| Confusing init menu shape | `jira-flow init` is both an initialization command and a menu containing Status/Remove/Exit actions that conceptually belong at the root CLI level. |

## 7. Recommended v1 Architecture

Do not start by mechanically repairing every current function. The repository is small enough that a focused v1 refactor can remove more complexity than it adds.

### One executable

```text
jira-flow
|
+-- init
+-- status
+-- config
+-- link <ISSUE-KEY>
+-- unlink
+-- enable
+-- disable
+-- remove
+-- version
`-- hook
    `-- commit-msg <message-file>
```

The helper executables `commitmsg` and `postco` should disappear. The installed Git hook should call the same jira-flow binary with an internal hook subcommand.

### Persistent repository state

Repository configuration should survive process boundaries and be private to the repository by default. Two reasonable designs are:

- Git-local configuration: `git config --local jiraflow.enabled true`, `jiraflow.mode branch`, `jiraflow.issueKey ABC-123`, etc.
- A private file under the repository's Git directory, e.g. `<git-dir>/jira-flow/config.json`.

The important requirement is not the specific storage format. It is that every command and hook reads the same source of truth.

### Runtime flow

```text
git commit
    |
    v
managed commit-msg hook
    |
    v
jira-flow hook commit-msg <message-file>
    |
    +--> load repository config
    +--> disabled? return success without mutation
    +--> mode == branch? derive key from current branch
    +--> mode == manual? use linked issue key
    +--> no key? leave message untouched
    +--> already referenced? leave message untouched
    `--> update message safely
```

### Manual linking UX

A dedicated command is easier to understand than embedding a manual key in init:

```text
jira-flow init
jira-flow link ABC-123
git commit -m "feat(auth): add login"
git commit -m "test(auth): add login coverage"
jira-flow link ABC-456   # switch association
jira-flow unlink
```

Branch mode should simply derive a Jira key at commit time. It should not care which branch existed when JiraFlow was initialized.

### Hook coexistence

The v1 design must explicitly decide how it interoperates with existing Git hooks. A safe default is more important than convenience.

- Resolve the effective hooks directory through Git, including core.hooksPath/worktrees.
- Detect whether an existing commit-msg hook already exists.
- Never silently overwrite an unowned hook.
- Use a managed shim or documented composition mechanism when coexistence is possible.
- Record enough ownership metadata to remove only JiraFlow-managed integration.

### Release model

With one executable, GoReleaser can become the center of distribution. npm and Homebrew should be thin distribution wrappers around the same release assets, not independent naming systems.

## 8. Prioritized Remediation Plan

This is the order recommended for a local implementation agent. It deliberately fixes the product model before polishing CLI details.

### Phase 0 - Freeze and establish a baseline

- Do not add new user-facing features to the current architecture.
- Add a basic CI workflow and get the current repository building/testing in a clean environment.
- Create temporary-Git-repository integration-test helpers so future hook tests never touch the working checkout.
- Document current v0.5.0 behavior and intentionally unsupported paths.

### Phase 1 - Replace the state model

- Define persistent per-repository JiraFlow configuration.
- Separate `enabled`, `mode`, `issueKey`, and issue-key pattern semantics.
- Remove setup-time branch validation.
- Add explicit link/unlink behavior for manual mode.
- Make strict Jira-key validation and branch extraction separate functions.

### Phase 2 - Collapse to one binary

- Move commit-msg implementation behind `jira-flow hook commit-msg`.
- Delete the separate commitmsg and postco binaries.
- Remove post-checkout unless a concrete feature requires it.
- Eliminate npm-global-bin discovery from Go runtime code.

### Phase 3 - Rebuild hook management safely

- Resolve hook paths through Git.
- Support worktrees/core.hooksPath.
- Detect existing hooks and ownership.
- Refuse destructive overwrites.
- Make enable/disable/remove deterministic and idempotent.

### Phase 4 - Harden commit mutation

- Use safe whole-file reads/writes.
- Make Jira-key insertion idempotent.
- Decide/configure how Jira references coexist with Conventional Commits.
- Handle detached HEAD and no-match branches as normal non-fatal states.
- Keep hooks quiet on successful no-op behavior.

### Phase 5 - Rebuild testing

- Add end-to-end tests for automatic and manual modes across separate processes.
- Test hook coexistence and removal safety.
- Test nested directories, worktrees, core.hooksPath, detached HEAD, and unusual branch names.
- Test CLI help/version outside repositories.
- Run CI across the operating systems/architectures that are truly supported.

### Phase 6 - Simplify release/versioning

- Choose Git semver tags as the canonical version source.
- Inject version metadata into the Go binary.
- Remove Changesets unless there is a concrete multi-package need.
- Generate one GoReleaser artifact contract and align npm/Homebrew with it.
- Delete unsupported/broken installers rather than advertising them.

### Phase 7 - v1 UX/polish

- Normalize naming to `jira-flow` for the command/package and `JiraFlow` for the product name.
- Move Status/Remove/Enable/Disable out of the init menu and into explicit commands.
- Update README examples to match tested behavior exactly.
- Publish migration notes from v0.5.0.

### Recommended compatibility stance

Because the current repository state is pre-1.0 and contains fundamental implementation problems, preserving internal behavior should not be a primary goal. Preserve the product promise and reasonable CLI affordances where useful, but prioritize correctness and safety. A small breaking change now is cheaper than encoding the current hook/config behavior into a stable v1 contract.

## Final Assessment

JiraFlow is worth improving. The concept is narrow, useful, and small enough to rebuild cleanly. The current problem is not that the idea needs more features; it is that the existing implementation has too many separate sources of state and too many distribution paths for such a small core behavior.

The strongest v1 is likely smaller than v0.5.0: one binary, one persistent repository state model, one commit hook, one safe hook-management path, one release source of truth, and tests built around real temporary Git repositories.

> Key maintainer decision: treat v0.5.0 as a prototype implementation whose public idea should be preserved, not as an internal architecture that needs to be kept compatible.
